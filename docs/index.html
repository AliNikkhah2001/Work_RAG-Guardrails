Overview

Persian-aware safety policy boundary and guarded Gemma gateway for the Work Credit RAG platform.

Implemented & Live Summary

Guardrails owns policy enforcement around the self-hosted Gemma generation service. Status: implemented and live on Vast.ai (vast-gemma4-migration). Deterministic Persian rails + risk scoring + semantic interface.

nemoguardrails has been removed. The service now runs deterministic signals + a direct-LLM judge (one-LLM Yes/No self-check) with fail-closed behavior. No NeMo / Colang flow is executed at runtime.

Design goal: fail closed — if the policy engine errors or times out, the request is refused rather than passed through.

In the MVP request path Guardrails:

  • Runs deterministic input/output checks before retrieval and generation
  • Emits evidence signals (injection, jailbreak, HurtLex hate, profanity, scope, PII) that the LLM judge weighs — detectors do not block directly, except secret
  • Runs a direct-LLM judge self-check (one LLM Yes/No call) as a second opinion
  • Serves an OpenAI-compatible guarded Gemma gateway (POST /v1/chat/completions)
  • Returns structured decisions and stable refusal responses
  • Exposes health/readiness endpoints and a Persian dashboard on :8200

Diagram terms — every element explained

  • ORCH — Orchestrator :8100: The request coordinator (Work RAG Orchestrator service) that fronts the public API and asks Guardrails to run an input rail check before touching the knowledge base.
  • GR — Guardrails :8200: The guardrails service itself. Runs deterministic signals plus a direct-LLM judge; nemoguardrails/NeMo has been removed and is no longer executed at runtime.
  • GE — Gemma: The generation model, reachable at :18000 on Vast.ai or :9000 on the H200 manager host.
  • Arrow 1 — POST /v1/rails/check: The input rail check call from the Orchestrator to Guardrails (stage=input) before any retrieval happens.
  • Arrow 2 — POST /v1/chat/completions: The guarded, OpenAI-compatible Gemma generation call that Guardrails makes (or proxies) to the upstream model.
  • Generated text (GE → GR): Raw model output flows back into Guardrails so output rails can be applied before the answer reaches the user.
  • Arrow 3 — output rails + PII mask: Guardrails applies output safety rails (PII masking, hard block on secrets, hate/profanity checks) and returns the final safe response to the Orchestrator.

Diagram terms — every element explained

  • IN — input text: The raw user query entering the guardrails pipeline (Persian or any language).
  • PIPE — signals → judge → self-check: The three-stage adjudication pipeline: deterministic detectors emit evidence, the policy judge weighs it, and a direct-LLM self-check provides a second opinion. nemoguardrails is removed.
  • OUT — decision: allow / refuse: The final verdict. On any block, Guardrails returns a premade refusal (finish_reason="content_filter"); on allow, generation proceeds.
  • IN → PIPE: Input text is fed into the adjudication pipeline.
  • PIPE → OUT: The pipeline produces the allow/refuse decision that gates generation.

What Guardrails does not own

Guardrails does not own retrieval, conversation orchestration, the frontend, or model serving. Only Guardrails calls the Gemma manager in the MVP path. It is a policy enforcement boundary sitting between the Orchestrator and Gemma.
